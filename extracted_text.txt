HOW TO USE THIS CHECKLIST
1.  Work through each issue row in the table on the following pages.
2.  Read the "What was found" column to understand the original problem.
3.  Apply the fix described in the "Fix required" column, referring to the Remediation Guidance Notes (RG) document for full code examples.
4.  Re-test the fix using the self-check tools listed in the box below.
5.  Once the fix is verified, write "Fixed" or "N/A" in the "Developer confirms" column and add your initials.
6.  Complete the sign-off block at the end of this document and return the signed checklist to the auditor.
Important: Do not mark an issue as fixed until you have re-tested it with at least one of the self-check tools listed below. Visual inspection alone is not sufficient.
SELF-CHECK TOOLS — Use these to verify fixes before marking as confirmed
axe DevTools — Browser extension (Chrome/Firefox). Scan each fixed page and confirm the previously reported violation no longer appears. Download: deque.com/axe/devtools
NVDA Screen Reader — Free screen reader for Windows. Use with Chrome to verify alt text, form labels, heading structure, focus order, and status messages. Download: nvaccess.org
HeadingsMap — Chrome/Firefox extension. Verify the heading hierarchy is correct after heading structure fixes (H1 present, no skipped levels, no widget headings). Available in browser extension stores.
Chrome Accessibility Inspector — Built into Chrome DevTools (Elements > Accessibility tab). Check the accessible name, role, and value of any interactive element after SC 4.1.2 fixes.
W3C Nu HTML Validator — Online validator at validator.w3.org/nu/ — paste the live page URL and confirm no errors remain after SC 4.1.1 parsing fixes.
WCAG Colour Contrast Checker — Browser extension or webaim.org/resources/contrastchecker/ — verify each fixed colour pairing achieves the required 4.5:1 ratio (or 3:1 for large text) after SC 1.4.3 fixes.

Complaints Board table: add <caption>Trend of Annual Disposal of Complaints</caption> inside the <table> tag. Add scope="col" to every column header: <th scope="col">Sr No</th>.

A-03
Level A
SC 2.1.2
HOME PAGE — A KYC Client Consent Form modal opens when the user clicks "Get Started". The modal cannot be dismissed by pressing the Escape key.
Keyboard Tab navigation becomes stuck inside the modal area. No input fields within the KYC form (PAN Number, Date of Birth, Phone Number, Email ID) are reachable by keyboard Tab navigation.
Keyboard-only users who trigger this modal have no way to close it or interact with the form using the keyboard alone.
Add Escape key handling so the modal closes when ESC is pressed: document.addEventListener("keydown", function(e) { if (e.key === "Escape") { closeModal(); } });
The closeModal() function must: (1) hide the modal, (2) remove the overlay, (3) return focus to the element that triggered the modal.
When the modal opens, move focus into it immediately: document.querySelector("#kyc-modal-close").focus();
Ensure all form inputs (PAN Number, Date of Birth, Phone Number, Email ID) are native <input> elements or have tabindex="0" so they enter the natural tab order.
Implement a focus trap: when Tab reaches the last focusable element in the modal, cycling Tab must return to the first focusable element inside the modal.
On modal close, return focus to the trigger element: triggerElement.focus();
Self-check: open modal with mouse, press ESC — modal must close and focus must return to the page. Re-open, Tab through all fields, confirm all are reachable. See: RG Issue 03

A-07
Level A
SC 4.1.1
W3C Nu HTML Validator confirms a <style> element used as a direct child of a <form> element — this is not permitted by the HTML specification.
The <form id="kyc-form"> element is not correctly closed. The validator reports an unclosed form element which causes unpredictable DOM construction.
A <style> element appears as a direct child of <body> following a closing </div>. Inline style blocks must be placed inside <head>.
A heading h4 (computed level 4) follows a heading h2 (computed level 2) skipping level h3 entirely — a structural parsing violation.
Move all <style> blocks into the <head> section of every page. Remove any <style> elements that appear inside <body>, <form>, or other non-permitted parent elements.
Locate and correctly close the <form id="kyc-form"> element. Ensure every opening <form> tag has a correctly positioned matching </form> closing tag.
Fix the heading hierarchy: after any h2, the next lower heading level must be h3. Change the h4 that follows h2 to h3, or restructure content so heading levels are not skipped.
Run the W3C Nu HTML Validator (validator.w3.org/nu/) on every page after making changes and resolve all remaining errors.
Self-check: re-run axe DevTools after validator fixes and confirm the parsing errors no longer appear. See: RG Issue 07

SC 1.4.11
HOME PAGE — The "Start Now" and "Get Started" buttons in the auto-advancing Daily Market View and Community Engagement cards have a button boundary contrast ratio of 1.05:1 against the adjacent gradient background.
The visual edge of these buttons is not distinguishable from the surrounding background. Users who cannot perceive colour reliably cannot identify where these interactive elements begin and end.
Requirement: interactive UI component boundaries (button borders or button backgrounds) must achieve at least 3:1 contrast against adjacent background colours.
Option A — Add a solid border to each button in a colour that achieves 3:1 against the adjacent gradient: border: 2px solid #FFFFFF; (white border on the dark gradient).
Option B — Replace the gradient button background with a solid colour that achieves 3:1 against the surrounding area. Test the exact gradient colour at the button position using the browser DevTools colour picker, then verify the contrast at webaim.org/resources/contrastchecker/.
In your CSS, target the specific button classes for these cards: .daily-market-btn, .community-btn { border: 2px solid #FFFFFF; } — adjust the selector to match your actual class names.
Self-check: use the WebAIM Contrast Checker inputting the button colour and the exact background colour adjacent to the button edge — must achieve 3:1. See: RG Issue 11

Level AA
SC 3.1.2
LEGAL & RISK DISCLOSURE PAGE — The final line of the page body is written in Hindi. The surrounding HTML element has no lang="hi" attribute.
The page-level language attribute is lang="en". Screen readers will attempt to read the Hindi text using English pronunciation rules, producing unintelligible output for any user relying on text-to-speech for this content.
Find the HTML element containing the Hindi declaration on the Legal & Risk Disclosure page and add lang="hi" to it: <p lang="hi">Hindi text here</p>.
If the Hindi text is inside a <div> or <section> that also contains English content, wrap only the Hindi portion in a scoped element: <span lang="hi">Hindi text here</span>.
If your CMS uses a rich text editor, look for a language selector option when editing that paragraph — some editors allow setting the language of a text block directly.
Self-check: use NVDA configured with a Hindi voice profile — the screen reader must switch to Hindi pronunciation for the marked passage and return to English for surrounding content. See: RG Issue 12

Level AA
SC 3.3.4
HOME PAGE — The KYC Client Consent Form collects PAN Number, Date of Birth, Phone Number, and Email ID for client registration with a SEBI Registered Research Analyst. This constitutes a legal and financial submission.
On clicking the final submit action there is no review step, no confirmation screen, and no opportunity for the user to verify or correct their entered data before it is processed and committed.
Option A — Add a review / confirmation step before final submission: after the user fills all fields and clicks Submit, show a summary screen listing all entered values (PAN, name, date of birth, phone, email). Include an Edit button that returns them to the form and a Confirm & Submit button that completes the submission.
Option B — Add a required confirmation checkbox at the bottom of the form before submission: <input type="checkbox" id="confirm" required> <label for="confirm">I confirm that the information I have provided is accurate and I consent to its use for KYC registration.</label>
Option C — After submission, send a confirmation email containing the submitted data and a link to update or cancel the registration within a defined time window.
Whichever option is chosen, ensure the form is fully keyboard accessible (see Issue A-03 / SC 2.1.2) so the review or confirmation step can be completed without a mouse.
Self-check: submit the KYC form and confirm the user has an opportunity to review or confirm their data before it is finally committed. See: RG Issue 13
